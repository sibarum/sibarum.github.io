Nanobuf · code golf

Nanobuf, golfed.

Nanobuf is a serialization format built so that its reader and its writer each fit on one line of a shell. This page asks the obvious next question: how short can they get in other languages? Every entry here passes the same test cases, and fewer bytes wins.

They are written to be used rather than to win: they print an error message, which golf entries may skip. They are tested by intrabuf's own suite, not by the harness on this page.

Rules

What an entry has to do

An entry is two lines: a reader and a writer, each a function (or the language's closest equivalent) that someone could paste into a program.

  • The reader takes a path, a schema name and a major version. It hands over every row after the header, kind first, by returning them or by calling a function once per row. It refuses a file whose header names another format version, another schema or another major version, and a file with no header. Fields are UTF-8 text, or bytes that are UTF-8.
  • The writer takes a path and a row's fields. It appends one record to the file: the fields joined by 0x1F, then 0x1E and a line feed, in UTF-8 with no byte order mark. It refuses a field that contains 0x1E, 0x1F or NUL, and then writes nothing.
  • Refusing means any failure the caller can catch: an exception, die, a Tcl error, None or Nothing, or a non-zero result. The entry doesn't have to print a message.
  • The count is the UTF-8 length of the line. Imports, usings and #includes that a file of that language normally opens with are listed under each entry and not counted. Everything else is.
  • A missing field reads as empty, so a reader may drop empty fields at the end of a row. Perl's split does that for free.

Every entry runs against these 18 cases. Each language's line goes into a small driver that the harness builds and runs as its own program:

  • Reads what the reference writes. The rows include empty fields, empty trailing fields, tabs, line breaks inside values (CR LF among them), a value that starts with a line break, a lone CR, non-ASCII text, every shell's special characters, a row with only a kind and a row with thirteen fields.
  • Reads the same file without its final line feed; with CR LF, a lone CR, or nothing at all after every record; and after Git's line-ending conversion, which turns every LF into CR LF, inside values too.
  • Reads a header with no rows, and ignores a truncated final record: whatever follows the last 0x1E is not a record.
  • Refuses another schema, a schema that is a prefix of the real one, another major version, a file at major 11 when asked for 1, an empty file, and a file in nanobuf version 2.
  • Writes a file byte for byte identical to the reference's, and refuses 0x1E, 0x1F and NUL without writing anything. C strings can't hold NUL, so C skips that last case and runs 17.

The truncated-record case is the one addition to intrabuf's own cases, which the spec asks for. intrabuf's suite now checks it too, and every shell line passes it.

Perl

229 bytes

One regex with /g picks out every record that ends in 0x1E and eats the line break in front of it, so a truncated tail never matches. The header is checked as a regex on the raw record, where \c_ is 0x1F. The writer checks all the fields at once by testing "@_", the fields joined with spaces.

Writer · 88 bytes

Try it

Run the harness, or beat a line

The entries, their drivers and the harness are in nanobuf-golf. With Java 25 or later, from that folder:

java Golf.java            # every language
java Golf.java perl tcl   # just these

It prints each entry's byte counts and which cases fail. It runs on Windows for now, because that's where it finds the C, C#, JScript and VB compilers. The languages here are the ones the test machine already had. Python, JavaScript, Ruby, Go, Lua and PHP come next. A shorter line that passes every case replaces the one here.
