01 · PontifA programming language on GraalVM Truffle

Pontif

Types that are claims the compiler proves, not annotations it trusts.

Pontif is a language for building real programs: modules, three kinds of polymorphism, operator overloading, a native GUI and plotting, and computations compiled to the GPU at runtime. A refined type such as [Int:@>=0] is a proof obligation. A match is checked for totality, a declared return is proved or the program is rejected, and when the built-in prover can't close a claim, you write the missing step in an assign proof beside the code.

There is deliberately no SMT solver. The prover is small enough to read end to end, and what it concluded is written out as plain text you can review: the receipt graph, the conservation ledger, and a Narrowings view that shows your program with every type replaced by what was inferred.

  • Conservation ledgers. proof translate = DataConservative() proves every field of the input reaches the output. Drop one and the error names it.
  • One door for effects. Side effects enter through emit. An action's parameter type is its filter, and an event nobody consumes is an error.
  • Three backends from one IR. Truffle for a JIT on the CPU, GLSL, and SPIR-V on Vulkan. CLI and editor both build as native executables.
  • The docs compile. Every runnable snippet in the README and guide is a test, so the documentation can't drift from the language.

module ledger

struct Account(balance:[Int:@>=0])
struct Txns(amount:Int, rest:[Txns|Done])
struct Done()

method Account.deposit(n:Int):Account -> match n {
  [@>0]  -> Account(this.balance + n)
  [@<=0] -> this
}

function totalIn(ts:[Txns|Done]):Int -> match ts {
  [Txns] -> ts.amount + totalIn(ts.rest)
  [Done] -> 0
}

Account(0).deposit(totalIn(Txns(100, Txns(50, Done())))).balance   # → 150

02 · COTTTraction, a number model: a Lean 4 specification and the calculator that implements it

COTT

A calculator that divides by zero, and a proof that it may.

In traction, a value is a pair (p, q) that is never reduced. Q(1, 2) and Q(2, 4) are different values, q = 0 is allowed, and 0/0 is a value like any other. The same pair can be read as a complex number, a difference, a sum, a ratio, a product or a logarithm. Each reading has its own arithmetic, and moving between them is always an explicit conversion.

Because nothing is divided away, nothing is lost. An inverse returns to 1 with its norm kept as a residue, failing exactly where the product loses information, and x − x remembers what cancelled.

  • cott-lean is the specification. Every theorem holds for every pair, none is checked on a sample, and CI checks that every declaration uses only Lean's standard axioms.
  • cott-engine implements it, and cites it. Every operation names the Lean definition it implements, and every test names the theorem it states. A citation to a renamed or missing declaration fails the build.
  • Classical where it is classical. The pages say which parts are textbook (ℤ[i], wheels, Möbius maps) and which are new: one unreduced carrier for all of them.
  • On your desktop. VexelRay's Calculator is a window onto cott-engine.

03 · VexelRayA desktop stack for Windows and Linux: engine, GUI, framework, applications, and Ottermate

VexelRay

Desktop applications drawn live on the GPU that rest at zero frames per second.

VexelRay is a whole stack, from a Vulkan engine through to nine applications that know about each other: a file explorer that suggests instead of asking, an IDE, a terminal, a picture and video viewer, a calculator, physics sandboxes and more. A window draws when something changes and sleeps when nothing does, and the whole window is one draw call: a single SDF uber-shader draws shadows, lighting and text.

Each application is compiled ahead of time by GraalVM Native Image into one executable that runs without a JVM. The main thread only draws. App logic, disk work and time run on their own lanes, placed at compile time, so a part that hangs never freezes the window.

04 · SupirVastA shader and compute IR for Java and GraalVM

SupirVast

Write a kernel once. Run it on the GPU and the CPU, and check they agree.

SupirVast describes GPU programs as a typed, structured IR called core, and lowers it two ways: to validated SPIR-V that runs on any Vulkan GPU and cross-compiles to GLSL, HLSL and Metal, and to an executable Truffle AST that GraalVM JIT-compiles on the CPU.

Its test suite lowers the same program both ways, runs one on real hardware and the other on the JVM, and asserts the results are identical. So a shader's logic can be unit-tested with ordinary assertions, with no GPU, driver or capture tool, and then the identical IR ships to the GPU.

  • Generated from the spec. Every SPIR-V opcode, enum and operand comes from Khronos's machine-readable grammar, not a hand transcription.
  • Real GPU features. Structured control flow, atomics, workgroup memory and barriers, and subgroup reductions, scans, shuffles and votes, all on both backends.
  • Tooling included. spirv-val, spirv-opt, spirv-cross and friends are fetched from a pinned Vulkan SDK and bundled.
  • Under everything. VexelRay's shaders are compiled to SPIR-V through it at build time, and Pontif's on Gpu kernels lower through it.

05 · Atchung! ElektroQ!Transport-agnostic message passing for the JVM and native images

Atchung! ElektroQ!

Something happened, here or across the wire. Your code doesn't have to care which.

Atchung! is a realtime, multithreaded publish/subscribe bus inside one process: zero-copy, no dependencies, no reflection. ElektroQ! moves the same typed messages between processes and machines, over TCP, Unix domain sockets or in-process, with codecs generated at compile time from annotated records. A bridge joins them, so a topic on the local bus can cross the wire without its publishers or subscribers changing.

The rule that holds the design together: the fast in-process path never pays for the network. Going cross-process is opt-in and lives entirely in ElektroQ! and the bridge.

  • Three ways to receive. Inline on the publisher's thread, async on your executor, or pumped and drained on your own thread once a frame.
  • Backpressure you choose. Drop oldest, drop newest, coalesce to the latest, block, or fail loudly rather than lose an event.
  • One order for many components. A Tick delivers to many inboxes in rounds, in the same order whether it runs on one thread or several.
  • Native-image ready. No reflection anywhere, so the whole stack compiles to a native binary with no reachability configuration.
